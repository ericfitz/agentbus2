# ADR 0011: One access check

Status: Accepted (Eric, 2026-10-25); amended by Eric's decisions of 2026-10-26 (section "Eric's decisions of 2026-10-26" below: the `List` rule, the `Unsubscribe`, `FilterReceive` and `TakeName` actions, the protocol version)

Covers Eric's decisions of 2026-10-25 recorded in `docs/superpowers/specs/2026-10-25-accesscheck-design.md` sections 1, 4 and 4.1 to 4.8 (the spec numbers them "accesscheck 1" and "accesscheck 2", questions 1 to 12 and the rulings that followed). The implementation plan is `docs/superpowers/plans/2026-10-25-accesscheck.md`. Every decision below is labeled as Eric's; the mechanics that follow from them are the agent's design, and the spec says which is which. Amends ADR 0008 (its decision 1 and the Milestone 3 addendum), ADR 0009 (decisions 8, 11, 12 and 19) and ADR 0004 (the Store contract; see its addendum "Access facts, not rules").

## Context

The rule "who may do what to which object" was computed in many places: `Core.Authorize` and `ReadableChannelIDs` in `internal/core/authz.go`, two Store SQL statements (`EffectivePermissions`, `ReadableChannels`) that agreed only by inspection, administrator checks in a dozen handlers, a task-owner guard, a client-side memory filter (`internal/agentview`), client-side access decisions in the TUI, and rule reads of the Slack bridge. The spec's Appendix A lists every site found at commit 0333662.

## Decisions (Eric, 2026-10-25)

1. **One access check.** Eric's words: "The right way to check if someone has access to something is accesscheck(principal, object). We should NOT have multiple different pieces of code each attempting to calculate this on their own. We need to implement a single accesscheck method, centralize all our business rules (admin, owner, etc.) into that piece of code, and use that everywhere." (accesscheck 1)
2. **This lands before the channel-visibility work**, which is rebuilt on it afterwards; its `Tx.VisibleChannels` query is a second statement of the rule and is not built. (accesscheck 2; spec 3.10)
3. **The rule lives in `internal/core/access`.** `decide(principal, facts, action)` in `decide.go` is the only code that decides. `Check` loads the facts and returns a `Decision{Allowed, Code, Text, Reason}`; `Require` turns a denial into a `bus.Error`; the set forms are `Channels`, `Identities` and `Holders`. The Store serves facts only: `Tx.ACL`, `Tx.ACLRowsFor`, the channel, identity and session rows. `EffectivePermissions` and `ReadableChannels` are deleted from the Store contract (answer to question 9; ADR 0004 addendum). Action by object:

   | Object | Actions |
   | --- | --- |
   | Channel | `Read`, `Write`, `Admin`, `List`, `Unsubscribe`, `FilterReceive`, `Deliver`, `Post` |
   | ACLChange | `ReplaceACL` |
   | Server | `Administer`, `CreateChannel` |
   | Session | `Use` |
   | Identity | `See` |
   | ChannelName | `TakeName` |
   | ScopeName | `TakeName` |

   The `Unsubscribe` and `FilterReceive` rows and the two `TakeName` rows record Eric's decisions of 2026-10-26 (below); for `TakeName` the rule is his, while the action name, the object names `ChannelName` and `ScopeName` and the Reason `name_prefix` are an agent choice. An action not defined for an object is `internal`; `Anonymous` is denied everything.
4. **The governing principle (4.4).** Scopes limit agent identities only; they backstop ACLs. Humans and administrators are never restricted by a scope. An ACL does not embed a scope, but an object with an ACL may have one. For a scoped agent the effective access is the intersection of its scope and the ACL: an object outside the agent's scope is denied; inside it the agent gets exactly what the ACL grants. An administrator and a human get what the ACL grants (the administrator also the implicit grants that keep every object manageable).
5. **The rule table (spec 3.2), after the scope gate.**

   | Object | Action | Allowed when |
   | --- | --- | --- |
   | Channel | Read, Write | the union of the stored rows for the principal's name, `everyone`, `humans` if the principal is human, and `admins` if the principal is an administrator holds that permission (Decision 80) |
   | Channel | Admin | that union holds `admin`, or the principal is an administrator (the implicit `admins` entry grants `admin` only, never `read` or `write`) |
   | Channel | List | a stored row for the principal's name, `everyone`, `humans` if the principal is human, or `admins` if the principal is an administrator, or the administrator flag; no creator clause (Eric's decision 2026-10-26 (1)). This replaces the interim clause "every channel in scope", which kept Decision 94 (superseded) |
   | Channel | Unsubscribe, FilterReceive | the scope gate alone: no stored row is needed (Eric's decision 2026-10-26 (2)) |
   | Channel | Deliver | Read, and not (an agent and a memory channel) (decision 20 moved in; question 4) |
   | Channel | Post | a human with Write (the bridge; ADR 0009 decision 11) |
   | ACLChange | ReplaceACL | Channel Admin, and, for an agent that is not an administrator, no protected entry loses a permission (decision 9 below) |
   | Server | Administer | the administrator flag; never for a scoped principal |
   | Server | CreateChannel | `channel_creation` is `open`, or the principal is an administrator (Decision 93) |
   | Session | Use | the session's identity is the principal's |
   | Identity | See | the scope gate, which admits every human and every administrator |
   | ChannelName | TakeName | a scoped principal's channel is named `<scope>-<rest>`, and a name starting `<s>-` for a scope `s` (any state) belongs to `s`; code `validation`, Reason `name_prefix` (the rule is Eric's decision 2026-10-26 (3); the action, object names and Reason are an agent choice; decision 19 below) |
   | ScopeName | TakeName | the new scope's `<name>-` prefix nests with no existing scope's (any state) and no channel of another or no scope is named `<name>-*`; code `conflict`, Reason `name_prefix` (the rule is Eric's decision 2026-10-26 (3); the action, object names and Reason are an agent choice; decision 19 below) |

   **The scope gate runs first.** A principal with no scope is never restricted. A scoped principal is denied an object outside its scope: a channel whose scope differs (an unscoped channel, `general` included, is outside every scope), a task or memory of such a channel, and an agent identity of another or no scope. `CreateChannel` is the one exemption (the new channel takes the creator's scope, ADR 0009 decision 8); a session is always the caller's own; the server is never in scope for `Administer`.
6. **Denial codes.** An out-of-scope denial is `not_found` with the text the operation uses for a thing that does not exist (`channel %q does not exist`, `identity %q is not registered`, the memory and task texts), Reason `out_of_scope`: a scoped identity cannot learn what exists outside its scope (4.1 (d)). A missing permission is `forbidden`, `%s needs %s on channel %q` (Reason `no_permission`). `Administer` and the `admins` form of `CreateChannel` are `forbidden`, `administrator privilege required` (Reason `not_admin`). `Deliver` of a memory channel to an agent is `validation` (Reason `memory_channel`). `Post` by an agent is `forbidden`, `%s is not a human` (`not_human`); by a human without write, the `no_permission` text (`no_write`). Another identity's session is `not_found` (`not_owner`). A deleted identity is `not_registered`. The codes of the ACL matrix, `TestAuthEndToEnd` and the e2e table are unchanged.
7. **The administrator gate anchor moves.** `scripts/check-gates-selftest.sh` block 15 mutates `internal/core/access/decide.go` at `if !p.Admin {` (present exactly once there; the `Server`/`Administer` clause) and expects `TestAuthEndToEnd/sqlite/admin-refused-as-non-admin` to fail. This supersedes the health plan's constraint "never edit `RequireAdmin`": the constraint protected the anchor, and the anchor now guards the single rule. Approved (question 10).
8. **The regression net.** `TestAccessRuleSites` (`internal/core/access/sites_test.go`, go/ast, the pattern of `TestPutPublicKeyCallers`) fails when code outside `internal/core/access` makes an access decision: a selector of `Admin`, `Creator`, `Owner` or `Scope`, or of an identity `Kind`, anywhere in a function or a package-level initializer (conditions, returns, assignments, literals and arguments alike), or a `store.Perm*` constant in a condition; the memory `Kind` anywhere, over the server side plus `internal/mcpserver` and `internal/cli`; a two-argument `ACL(` call on any receiver from an unlisted function; or SQL in `internal/store/sqlstore` that filters on `is_admin`, `can_read`, `can_write`, `can_admin` or `creator` (regexps). The allowlist is a literal in the test that names, per function, the exact number of occurrences of each clause it exempts, and one occurrence more or fewer fails the gate, so adding a site, or a second rule to a listed one, is a visible edit with a review question attached (issue #19; `scripts/check-gates-selftest.sh` block 29 proves each clause fires). The test's comment lists what it still does not see. `TestChannelsAgreesWithCheck` (`internal/conformance/access`) proves the set form agrees with the single-object form, and `TestACLMatrix` (52 leaves per engine) is untouched and proves the moved rule is the same rule.
9. **Protected ACL entries (4.6).** An agent, scoped or not, must never remove any permission held by an administrator or a human in any ACL. The protected entries of a stored ACL are every entry naming a human, every entry naming an administrator, `admins`, `humans` and `everyone`. Any loss counts, a deleted entry or a reduced permission set. A human or an administrator holding `admin` on the channel may still change them. The check is the `ReplaceACL` action; the denial is `forbidden`, Reason `protected_entry`, `an agent cannot remove %s from ACL entry %q: humans and administrators keep their access`. Not covered, each considered in the spec: `CreateChannel` with an explicit `acl` (nothing stored to lose), `RenameChannel`, scope retirement, the bridge's own `tx.SetACL` calls.
10. **Humans are never scoped and, with administrators, visible to every agent (4.5).** Assigning a scope to a human fails `validation` (`a human identity cannot be scoped`); a stored human row with a scope is normalized on read and repaired by maintenance, by the mechanism of decision 11. `Identity/See` admits a human or an administrator before the scope comparison, so a scoped agent can name them in an ACL and as a task owner and sees them in `Identities`. An agent outside the scope stays invisible.
11. **An administrator is never scoped (4.3, replaces 4.1 (a)).** "An admin is an admin. Admin is incompatible with scopes." Making an identity an administrator (`MakeAdmin`, `admins add`) clears its scope; creating or scoping an administrator fails `validation` (`an administrator cannot be scoped`); an identity read that finds both repairs the value in memory and logs an error; `Identities.ClearInvalidScopes` repairs the stored row on each maintenance pass under the maintenance lock (a second run finds nothing; replicas exclude each other by the lock).
12. **The `humans` group (4.7).** A derived ACL group beside `everyone` and `admins`: its members are the identities of kind human, no list is stored, the name is reserved (`store.Humans`, included in `store.ReservedIdentity`). It needs no schema change. A `humans` entry is protected (decision 9). The `default_acl` setting accepts it.
13. **Rulings of 4.8.** (1) Deleting a channel is not covered by the protected-entry rule: an agent with `admin` on a channel may delete it; deletion removes the object, not a grant. (2) `humans` with `read` or `write` is forbidden on a bridged channel, in `CheckBridgeACL`, like `everyone` and `admins` (ADR 0009 decision 12), so the Slack invite list stays explicit. (3) An agent can never make a default-ACL channel private afterwards (the `everyone [read, write]` entry is protected); it creates a private channel with an explicit `acl`. The skill and the MCP `create_channel` description say so in one sentence.
14. **The implicit creator entry is retired (question 6; spec 3.13).** Server administrators implicitly may discover any channel and hold `admin` on it; nobody holds an implicit `read` or `write`. `channels.creator` stays as data. A channel created without an ACL keeps the creator's `admin` through the stored Decision 88 default row; one created with an explicit ACL that omits its creator loses it (`docs/ops/upgrade.md` has the operator query).
15. **No task owner guard (questions 1 and 12; spec 3.14).** Write access to a task list permits changing any task on it. `ownerGuardBlocked`, the `forced` revision, `TaskPatch.Force` and the wire member `force` are removed with every trace (MCP, CLI, TUI, skill). **Protocol change:** a request member is removed. Under the protocol-versioning decision a removal is major-shaped, but `info.version` was `2.0.0-dev` and no release has shipped, so it landed without a bump (superseded: `info.version` is `1.0.0` from 2026-10-26, decision 4 of the section below). A client that still sends `force` is not ignored: `TaskPatch` sets `additionalProperties: false`, so the server answers `validation` (HTTP 400). `owner` stays as data, with `task_claim`, `task_release`, the rule that an `in_progress` task needs an owner and the dead-owner reclaim. If agents misbehave without the guard, Eric revisits.
16. **The agent memory filter is on the server (question 4).** An agent principal is not delivered a memory channel through `receive`, `wait`, `watch` or the Stop hook's count (the `Deliver` action), and an agent's subscribe to one is `validation`; `internal/agentview` is deleted. The TUI's identity is human, so it is unaffected. A wake therefore always carries a count (ADR 0001 addendum).
17. **Bridge not configured is `unavailable`, not retryable (question 7)**, with the same text, replacing `forbidden`.
18. **Smaller rulings of section 4.** A session that is not the caller's stays `not_found` (question 2). The TUI's two client-side access decisions are removed; it reacts to the server's codes, and there is no `Can()` operation (question 3). Registration, sign-in and admission rules stay in `internal/core/identities` (question 5).
19. **Scope-prefixed channel names (4.2, option A).** A scoped identity creates or renames to names of the form `<scope>-<rest>` only; nobody outside scope `S` may take an `S-*` name; `CreateScope` refuses a name while a channel of another or no scope is named `<scope>-*`. This closes the one answer, a create or rename `conflict`, that would disclose an out-of-scope name. Eric's ruling (2026-10-25): existing names that violate the rule get no migration or compatibility handling (pre-release); the local stack's channels and scopes are deleted and recreated by hand. The decision is Eric's; implemented by `decide`'s `TakeName` action on `ChannelName` (channel create and rename) and `ScopeName` (scope create), gated by `TestScopeNamespace`. Moving the prefix rule into `decide` was issue #18, closed. Eric's decision 2026-10-26 (a controller ruling he ratified): `CreateScope` also refuses a name whose `<name>-` prefix nests with an existing scope's (any state), `conflict` `scope %q: the name prefix %q- overlaps scope %q`, so `job-2` stays usable beside `job`; and any channel creator can learn whether a scope `s` exists from the `<s>-` validation answer, an accepted consequence of the rule.
20. **The edges of "outside its scope" (4.1).** Recorded in the spec as Eric's decisions of 2026-10-25 and implemented as read there: (b) an ACL row naming a scoped identity on a channel outside its scope is accepted and inert (the scope gate runs first), and a scoped granter naming an agent it cannot see gets the Decision 96 text `ACL identity %q is not a registered identity` (amended by decision 10); (c) a scoped identity lists the identities of its own scope plus every human and administrator; (d) an out-of-scope denial is `not_found` (decision 6); (e) `general` is outside every scope; (f) the administrators' implicit right on every channel is the full channel-admin set; (review 1) scoped identities may create channels in their own scope; (review 2) the interim `List` clause (superseded by Eric's decision 2026-10-26 (1): `List` is a stored row or the administrator flag, and Decision 94, which the clause kept, is superseded). The spec's section 4.1 labels each of these as Eric's decision; this record follows it. Item (a) is replaced by decision 11.

## Eric's decisions of 2026-10-26

The visibility rebuild (`docs/superpowers/plans/2026-10-26-channel-visibility.md`, spec `docs/superpowers/specs/2026-10-25-channel-visibility-design.md` section 8) ran on this check. Each item below is Eric's decision 2026-10-26; what follows from it is the agent's design.

1. **Eric's decision 2026-10-26 (1): `List` is a stored row or the administrator flag.** The principal holds a stored ACL row on the channel (for its name, `everyone`, `admins` when an administrator, `humans` when a human: the names `Read` and `Write` already resolve), or is a server administrator. There is no creator clause, so a creator with no row lists nothing. The scope gate runs first. This amends his decision 2026-10-25 (1) (any ACL entry lists the channel; the implicit creator entry was retired by decision 14) and supersedes the interim `List` clause (decision 20, review 2) and Decision 94 ("every channel's name and kind are visible to any authenticated identity"; ADR 0008 and the design spec, each marked superseded). No Store query is added (the rule reads `Tx.ACL` facts, so `Tx.VisibleChannels` of the visibility spec 3.1 is not built and ADR 0004 gets no addendum).
2. **Eric's decision 2026-10-26 (2): Unsubscribe gets a dedicated scope-only action**, so `List` means one thing. Refined (option A): the scope-only gate is two actions, each named for its operation: `Unsubscribe` (Decision 95, `channels` unsubscribe) and `FilterReceive` (the channel filter of `receive`; leaving it on `List` would turn a filter on a row-less channel from "nothing delivered" into a denial). Both decide identically: the scope gate, then allowed. A reader whose rows were revoked can still unsubscribe and still name the channel in a `receive` filter. The names are Go constants of `internal/core/access`; the wire, MCP and CLI names do not change.
3. **Eric's decision 2026-10-26 (3): issue #18, both parts, closed.** The scope-prefix name rules (decision 19) are `decide` rules: `TakeName` on `ChannelName` (channel create and rename) and on `ScopeName` (scope create). `channels.namePrefixRule` and the `scopes.Service.Create` prefix and overlap checks are gone, and both entries left the `TestAccessRuleSites` allowlist; `TestScopeNamespace` and `TestScopeGateChannels` keep their codes and texts.
4. **Eric's decision 2026-10-26 (4): the protocol version is stamped.** `api/openapi.yaml` `info.version` is `1.0.0` and `internal/version.Protocol` equals it (a test pins them). The major is the `/v1` path, the minor is bumped per addition, the patch for a documentation-only change; `GET /v1/discover` and `GET /v1/health` (probe tier, beside `version`) carry a required `protocol_version`. No discovery capability string is added: the pending `channel_capabilities` name is moot. See the protocol-versioning section below and the ADR 0001 addendum.
5. **Eric's decision 2026-10-26 (5): channel `capabilities` and the bridged icon stand** as decided on 2026-10-25: a required string array, `[]` and never null, whose first value `bridged` means the channel's bridge is in state `live` exactly; every client passes unknown strings through and acts only on `bridged`. The TUI draws a bridged channel with the link icon (the emoji set 🔗, the Nerd Font set `fa-slack`).
6. **Eric's decision 2026-10-26 (6): search hits use the channel icon** of the rail, the header and the compose prompt: the chat bubble for an ordinary channel, the link icon for a bridged one, the tasks and memory icons as before (the blank mark for ordinary hits is gone).

Agent choices in the rebuild, not Eric's (each is one constant or one line to change): the `List` denial, which no caller sees (the set form drops the channel), is `forbidden`, Reason `no_permission`, text `%s holds no ACL entry on channel %q`; the name rule is one action, `TakeName`, on two objects, with Reason `name_prefix` (`validation` for `ChannelName`, `conflict` for `ScopeName`); the TUI health overlay shows the protocol version on its `server` line.

## Context: protocol versioning (Eric, 2026-10-25; implemented 2026-10-26)

Decided on 2026-10-25 for the rebuilt channel-visibility plan and implemented by it (Eric's decision 2026-10-26 (4)): `info.version` is `1.0.0`, `internal/version.Protocol` equals it, and `GET /v1/discover` and `GET /v1/health` carry `protocol_version`. The accesscheck work changed no wire field except the `force` removal of decision 15. The OpenAPI `info.version` is the protocol version, semver-shaped and decoupled from the build version: the major is the `/v1` path, the minor is bumped on every addition, the patch on a documentation-only change. `GET /v1/discover` and `GET /v1/health` expose `protocol_version` beside the build version. New additions no longer get a discovery capability string; the existing `long_poll`, `semantic_search` and `health` stay. This supersedes Decision 43's "additions get a capability" for additions (the visibility spec's pending `channel_capabilities` name is therefore moot: channel `capabilities` is part of `1.0.0`).

## Consequences

- One place to read and one place to change an access rule; a change elsewhere fails `TestAccessRuleSites`.
- A creator without a stored `admin` row no longer administers its channel.
- A scoped identity gets `not_found` outside its scope, and its set forms (list, receive, search, identities) show in-scope objects only. Before this record it saw and read `general` and every default-ACL channel.
- An agent cannot take a human's or an administrator's access away through `set_acl`, and cannot make a default-ACL channel private after creating it.
- The Slack bridge's who-may-post and who-is-invited questions go through `Check(Post)` and `Holders(Post)`: write through any additive row (a group row included) makes a human a poster; on a bridged channel the groups cannot hold read or write.
- Alternatives the spec rejected (section 3.11): keeping `core.Authorize` and friends as forwarders to `access` (two names for the rule, and a gate allowlist entry for each); a `Bus`-level `Can(object, action)` operation so clients stop mirroring rules (a protocol addition, not needed for this change); putting the checker in `internal/bus` so clients could run it (clients have no Store and the Bus error code is their answer).
- The channel-visibility plan's Task 1 and Review Focus 1 are superseded in part (spec 3.10); the rebuilt plan is `docs/superpowers/plans/2026-10-26-channel-visibility.md`, implemented (see "Eric's decisions of 2026-10-26").
