# ADR 0007: OpenAPI code generator

Status: Accepted (Eric, 2026-10-20)

Serves Decisions 3, 4, 19, 35, 42, 43, 46 and 47 of `HANDOFF.md` (all made
by Eric on 2026-10-19). The generator choice was the one open question
HANDOFF left. Covers Decisions 64, 65 and 91 (Eric, 2026-10-20).

## Decision (Eric, 2026-10-20)

Decision 64: oapi-codegen v2.8.0, as recommended below. Eric approved
the recommendation without changes on 2026-10-20.

## Context

Decision 4 makes the API OpenAPI-first: generators produce the server
framework and the client library, and the local MCP server is built on
that client. HANDOFF names oapi-codegen and ogen as the candidates and
asks for a spike against our needs: a strict server on `net/http`,
RFC 9457 errors, bearer and OIDC security schemes, and long-poll.

The spike was run on 2026-10-20 and is written up in
`docs/superpowers/specs/2026-10-19-codegen-spike.md`, with the rerunnable
spec, driver and tests in `docs/superpowers/specs/2026-10-19-codegen-spike/`
(`bash run.sh`). Versions: oapi-codegen v2.8.0 (released 2026-07-17,
requires Go 1.25), ogen v1.24.0 (released 2026-08-07), Go 1.27.2,
`CGO_ENABLED=0` throughout. The sample spec (OpenAPI 3.0.3) had four
operations: the well-known path, `GET /v1/discover`, the long-poll
`watch` and an idempotent `send`, with bearer and `openIdConnect` schemes
and a shared `application/problem+json` default response carrying `code`
and `retryable`.

## Evidence from the spike

Both generators generated, tidied, built, vetted and passed the same
tests (`RESULT: PASS`). By need:

1. Long-poll `watch` (200, bodiless 204, 409 problem+json, context
   cancellation): both pass. oapi-codegen returns typed response objects
   with a `Visit*` method; ogen returns a sum-type interface.
2. `default` response as `application/problem+json`: both honor it. To
   make the framework's own errors (bad parameter, missing header, failed
   security) problem+json, oapi-codegen needs three hooks
   (`StdHTTPServerOptions.ErrorHandlerFunc`,
   `StrictHTTPServerOptions.RequestErrorHandlerFunc` and
   `ResponseErrorHandlerFunc`, plus the validator middleware's
   `ErrorHandlerWithOpts` if used) sharing one helper; ogen needs
   `WithErrorHandler` plus a `NewError` that calls
   `ogenerrors.ErrorCode`, because its "convenient errors" route security
   failures through `NewError` and decode failures through the handler,
   and its default handler emits `application/json`, which its own client
   refuses to decode.
3. Two security schemes: oapi-codegen accepts `openIdConnect` and, since
   v2.8.0, generates no auth code at all (auth is middleware). ogen fails
   hard (`Feature "openIdConnect security" is not implemented yet.`);
   the `ignore_not_implemented` escape hatch drops the scheme from the
   generated server.
4. `Idempotency-Key` header on a mutating POST: both bind it and reject a
   missing header before the handler.
5. Dot in a path segment and `security: []`: both pass.
6. Decision 35, generated client over an in-memory `http.RoundTripper`:
   both work with a ten-line transport; ogen's client requires a
   `SecuritySource` even for unauthenticated operations and calls
   OpenTelemetry hooks on every request.
7. Server on plain `net/http`: oapi-codegen registers Go 1.22 `ServeMux`
   patterns on a mux the server owns; ogen generates its own radix router
   as an `http.Handler`. Neither needs a third-party router.
8. Pinning and freshness: both pin with a `go.mod` `tool` directive and
   regenerate deterministically, so `git diff --exit-code -- internal/gen`
   is a valid CI check for either.

Footprint: oapi-codegen generated about 1.6 k lines in one file and links
5 non-standard packages (24 with the embedded spec); ogen generated 4.6 k
lines in 19 files and links 79 packages from 27 modules, including
OpenTelemetry and zap, into every binary that imports the client (the MCP
server and CLI included). Both build with `CGO_ENABLED=0`.

OpenAPI 3.1: a copy of the spec with only the version changed generated
identically on both, but the sample used no 3.1-only features, so the
spike keeps 3.0.3 until a 3.1 feature is needed.

## Recommendation (Claude, accepted by Eric)

oapi-codegen v2.8.0 with `std-http-server`, `strict-server`, `client` and
`models`, authentication and authorization in hand-written `net/http`
middleware, pinned by a `tool` directive and regenerated by
`make generate` with a CI freshness check.

Reasons, in order of weight:

1. The only hard failure in the matrix is ogen's `openIdConnect`
   rejection, and its escape hatch removes the scheme rather than
   modeling it.
2. oapi-codegen generates no auth code, which is where Decision 8 (the
   server enforces authorization at the identity level) puts it anyway:
   in middleware the project writes.
3. The server stays plain `net/http` with `ServeMux` patterns beside the
   hand-written handlers, which fits Eric's "simple, clean code" goal, as
   does the smaller generated and linked footprint.
4. ogen's advantages (sum-typed responses, one error hook) come with the
   error-routing surprises in need 2.
5. oapi-codegen's cost is explicit and bounded: the error hooks sharing a
   `writeProblem` helper, and a lenient `*json` content-type match on the
   client, both visible in the spike test.

## The alternative: ogen v1.24.0

Choosing ogen would require:

- omitting the `openIdConnect` scheme from the OpenAPI document (or
  carrying `generator.ignore_not_implemented: ["openIdConnect security"]`
  and accepting that the generated server does not model it);
- `gen.WithErrorHandler` using `ogenerrors.ErrorCode`, and a `NewError`
  on the handler that also calls `ogenerrors.ErrorCode`, so every
  framework error is `application/problem+json`;
- a `SecuritySource` on every client, including the in-process local one;
- accepting OpenTelemetry and zap in every binary, or supplying no-op
  providers;
- type switches over sum-typed responses in the remote `Bus`
  implementation (Decision 47 keeps them behind the interface either
  way).

In exchange it gives sum-typed responses, `Opt*` wrappers instead of
pointers, a single error hook and a smaller generator module graph (51
modules against 127 with the `tool` directive).

## Consequences

- A `tool` directive for oapi-codegen pulls its module graph into
  `go.mod` as indirect requires; a separate `tools/go.mod` with
  `go tool -modfile` avoids that (not tested in the spike).
- Go 1.25 or newer is required.
- The validator middleware (`oapi-codegen/nethttp-middleware`,
  `kin-openapi`) becomes a server dependency if request validation
  against the embedded spec is wanted; otherwise the strict server's own
  binding is the validation.
- The hand-written MCP tool schemas (Decision 47) are kept in step with
  the OpenAPI document by hand, whichever generator is chosen.

## Decisions of 2026-10-20 (Eric)

- **Decision 65.** The OpenAPI document is version 3.1 and declares both
  the `http` bearer scheme and an `openIdConnect` scheme (option D of
  Question 2, after discussion; Claude had recommended 3.0.3 with bearer
  only). `GET /v1/discover` and the document's security schemes must
  agree.
- **Decision 66** (ADR 0001) keeps the `Idempotency-Key` header the spike
  used on the HTTP API; the MCP tools keep `idempotency_key`.

Consequences for this record:

- The evidence above that "the spike keeps 3.0.3" is overridden. The
  spike's 3.1 probe only changed the version string on a sample with no
  3.1-only features, and it never ran the kin-openapi request validator
  against a 3.1 document. Milestone 4 must re-test both generation and
  the validator (`oapi-codegen/nethttp-middleware`, `kin-openapi`
  v0.142.0 at the spike) on the real 3.1 document before relying on
  either; oapi-codegen's 3.1 support is new in v2.8.0 ("Initial OpenAPI
  3.1 support based on kin-openapi").
- The `openIdConnect` scheme needs an `openIdConnectUrl`. **Decision 91**
  (Eric, 2026-10-20, the spec's Question 27): it is the server's own
  `/.well-known/openid-configuration`, naming the token endpoint
  (`POST /v1/auth/token`, Decision 84) and the server's JWKS, since the
  server is the issuer (Decision 70, ADR 0002); `GET /v1/discover` returns
  the same URL and lists the configured external issuers. The server
  therefore serves an OpenID discovery document, which Milestone 4 adds
  beside `GET /v1/discover`.
- The ogen alternative would have been harder under Decision 65, since
  ogen rejects `openIdConnect`; the choice of oapi-codegen stands.

## Milestone 4 addendum (2026-10-21)

- **The 3.1 re-test.** Generation and the kin-openapi request validator are
  tested on the real OpenAPI 3.1 document (`api/openapi.yaml`, both security
  schemes) by the tests in `internal/gen` and `internal/server`, which run in
  `make test`; `make generate-check` and `scripts/check-gates.sh` check 4 fail
  a stale `internal/gen`.
- **Choice 6, the validator is adopted.** `nethttp-middleware` validates every
  request against the document embedded by a second generator config into
  `internal/gen/spec` (`spec.GetSwagger()`), imported by `internal/server`
  only. The validator is the security enforcement point: the `Authenticator`
  seam feeds its `AuthenticationFunc`. Its router answers an unknown path and
  a wrong method as 404. `internal/bus/remote` never imports `internal/gen/spec`
  or kin-openapi, so the MCP server and CLI of Milestone 6 do not link them;
  `scripts/m4-exit-checks.sh` enforces the Decision 47 import rule
  (`--deps-only` runs it alone, in CI). The measured
  `go list -deps ./internal/bus/remote | wc -l` is 207 packages (standard
  library included), against the count of 5 non-standard packages without the
  embedded document and 24 with it that this ADR gave.
- **Choice 7, discovery.** `auth_methods` is computed from
  `components.securitySchemes`; `capabilities` from what the core has
  (`long_poll` always, `semantic_search` with an embedder); the document's
  `openIdConnectUrl` is server-relative.
- **Choice 8 and pending item 2.** The auth operations (`/v1/auth/token`,
  `/v1/auth/jwks`) are not declared until Milestone 5; the
  `/.well-known/openid-configuration` response names them now and they answer
  404 `not_found` meanwhile (proceeded on recommendation A; test
  `TestOpenIDConfigurationNamesMilestone5Paths`).
- **Path-parameter facts.** The runtime's path styling uses `url.PathEscape`;
  the v2.8.0 std-http template binds `r.PathValue` with `ValueIsUnescaped:
  true`; the validator's router is built with gorillamux `UseEncodedPath()`, so
  `a%2Fb` reaches the handler as `a/b`; the empty segment is the only router
  404.
- **The body-read fact.** The validator reads every protected request's body
  before `AuthenticationFunc` runs and flattens its errors to plain strings.
  That is why the body limit is the outermost middleware with its own
  read-ahead, and why Milestone 5's authentication middleware sits in front of
  the validator, not inside it.
