# Milestone 7: Server Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two `agentbus2 server` replicas over one Postgres deliver and wake correctly and only one of them runs each maintenance job: the Postgres notifier (`NOTIFY` inside the append transaction, a `LISTEN` on a native pgx connection feeding the Decision 52 notifier, hints only, reconnecting), `pg_try_advisory_lock`-guarded maintenance with the SQLite lease row kept for local multi-process mode (Decisions 49, 68), the three maintenance deliverables Milestone 3 deferred (budget eviction, capacity notices, admin usage; Milestone 3 pending item 3 on A), a Docker image with a compose example over Postgres, and the operations docs.

**Architecture:** The Store contract grows two engine-neutral capabilities with engine-specific bodies behind the existing `Dialect` seam: `Locks` (`TryLock`/`Unlock`: the `leases` row on SQLite, a session advisory lock on a pinned connection on Postgres) and `Space` (`Usage`/`Reclaim`: `page_count` and `incremental_vacuum` on SQLite, `pg_total_relation_size` and a no-op on Postgres). The Postgres engine fills the `NotifyAppend` hook with `pg_notify` on a per-schema channel and gains a control hook on watch registration; the listener is a new package `internal/core/notify/pgnotify` that embeds `notify.Memory` for fan-out and owns one native `pgx.Conn`, wired by `agentbus2 server` when the store is Postgres. The core never names an engine: maintenance asks the Store for the lock and for usage, and the budget jobs act only where `Usage.Evictable` is true. The import direction stays store → nothing in core; core → store; the deps script of Task 7 enforces it.

**Tech Stack:** Go 1.27, `CGO_ENABLED=0`; `pgx` v5.11.0 (`pgx.Connect`, `Conn.WaitForNotification`, already in `go.mod`; no new module dependencies); `modernc.org/sqlite`; Docker 29 (multi-stage build, `gcr.io/distroless/static-debian12:nonroot`), Docker Compose v2; testcontainers from Milestone 1.

## Choices this milestone makes (delegated by the spec, recorded with rationale)

1. **Lock shape** (Decisions 49, 68; ADR 0004 "dialect hooks only where the engines really differ"). `store.Store` embeds `Locks{TryLock, Unlock}` (Store level, not `Tx`: an advisory lock is session-scoped, so it must live on one pinned `*sql.Conn` across the many transactions of a tick, and `Meta.TryLease` inside a `Tx` cannot hold it). SQLite: `TryLease` on the `leases` row inside a `Tx` (v1 `takeLease`, ported in Milestone 3), expiry at `until`; `Unlock` sets `expires_at = 0` for the owner. Postgres: `pg_try_advisory_lock(hashtext(current_schema()), hashtext($1))` on a `*sql.Conn` the Store keeps per name (keyed per schema as Milestone 2's migration lock is, so per-test schemas never contend); `now` and `until` are ignored; `Unlock` runs `pg_advisory_unlock_all()` on that connection and returns it to the pool (an `sql.Conn.Close` alone would hand the lock-holding session back to the pool). On both engines the Store remembers the `(name, owner)` pairs it holds and `Store.Close` unlocks each before closing the pool, so a clean shutdown frees the lock at once everywhere. The owner check is the Store's on both engines, before any SQL: when `s.held[name]` records a different owner, `TryLock` returns `(false, nil)` without touching the row or the pinned connection (two Cores over one Store handle, the shape of any in-process test or tool that shares a handle, never both run maintenance; the Postgres session lock alone would say `true` to a second owner on the same session), and `Unlock` by an owner other than the recorded one is a no-op. **Lifetime: held across ticks.** `Tick` calls `TryLock` every interval (a renewal on SQLite, a re-entrant re-assert on the pinned connection on Postgres, which also detects a dead connection and re-acquires on a fresh one), and `Unlock` runs once at shutdown (`cmd.Serve`). Rationale: the holder keeps maintenance until it dies or stops, so two replicas never alternate and the exit proof is crisp; failover is immediate on Postgres when the holder's session ends (clean shutdown or a dropped connection) and after `2 * interval` on SQLite (v1's bound). A silently partitioned holder keeps the Postgres lock until the server's TCP keepalive ends the session (`tcp_keepalives_idle`, Linux default 2 h); the deploy doc says to set it, in `postgresql.conf` or per connection through the DSN's `options=-c tcp_keepalives_idle=60 ...` (Task 8). **Why the longer partition window is accepted over acquire-per-tick/release-per-tick** (the alternative within the delegated space, which would shrink the window to the fraction of time a tick runs): (a) what that window costs is a pause of maintenance on every replica, never a double run or a lost row, and the jobs are idempotent either way (spec 5.7); the clean-shutdown and crash cases are already immediate (`Store.Close` unlocks; the session ends); (b) the exit proof depends on the holder being stable: with per-tick release two replicas legitimately alternate, so `one-holder` could no longer say "exactly one replica has any `ran true`" and would need start and end timestamps per tick to assert non-overlap, and the mutation blocks `advisory-lock-ignored` and `sqlite-lease-ignored` (Task 7 Step 4b), which expect `one-holder` to fail when the lock is ignored, would become flaky-to-vacuous, because ten fast jobs on a 1 s ticker in two replicas that ignore the lock may never overlap in wall time; (c) `TestTickTakesAndRenewsLease` on `main` already encodes "the holder renews, the second waits for expiry", which per-tick release would invert. `Meta.TryLease` stays on `Tx` unchanged (Milestone 3's tests use it).
2. **`NOTIFY` channel and payload** (Decision 52). One channel per schema, `'agentbus2_' || left(encode(sha256(convert_to(current_schema()::text, 'UTF8')), 'hex'), 24)` (`current_schema()` returns `name`; `convert_to` takes `text`) (34 bytes, always under the 63-byte identifier limit; `sha256()` rather than `md5()` because `md5()` errors under FIPS-mode OpenSSL), computed in SQL by both the `pg_notify(<channel>, $1)` call and the listener's `SELECT` before `LISTEN`, so a replica on another schema of the same database hears nothing. Payload `<channelID>:<seq>` for an append and `0:0` for a control hint (watch registration, pending item 1); `postgres.ParsePayload` accepts exactly `^\d+:\d+$`. `pg_notify` takes the channel as text (no identifier quoting). A Decision 26 retry sends its `NOTIFY` only from the attempt that commits.
3. **Listener** (`internal/core/notify/pgnotify`). `Listener` embeds `*notify.Memory`: `Publish` is the in-process fan-out the core already calls after commit (so the sending replica sees its own hint twice, which the one-slot coalescing absorbs) and the goroutine turns every notification into a `Publish`. One native `pgx.Conn` per listener (`pgx.ConnectConfig` with `application_name` `agentbus2-listen`, never the pool); on connect and on every reconnect it publishes `Hint{}` so armed watches re-check what they may have missed; reconnect with jittered exponential backoff from 100 ms to 5 s; `Close` is idempotent. The SQLite counterpart, `notify.Polling` (Decision 68), has no fan-out at all: on `main` its `Publish` is a no-op and only `Hint{}` ticks reach a subscriber (`TestPollingTicksAndIgnoresPublish` pins it), so no both-engine test may expect a published hint to arrive on SQLite; a both-engine test asserts the documented opposite there (Task 4's `TestNotifierPublishFanOut`). Package location: under `internal/core/notify` because it implements that package's interface and the core's wiring lives in `cmd`; it imports `internal/store/postgres` for the codec (store never imports core).
4. **Usage and reclaim** (Milestone 3 pending item 3's `Dialect.Usage`). `store.Usage{Bytes int64; Evictable bool}`: SQLite `(page_count - freelist_count) * page_size` (v1 `bus.go` `Usage`) with `Evictable true`; Postgres `sum(pg_total_relation_size(c.oid))` over `pg_class` rows of `current_schema()` with `relkind = 'r'` (tables with their indexes and TOAST; schema-scoped, unlike `pg_database_size`) with `Evictable false`, because relation size includes dead tuples until vacuum and deleting rows does not lower it promptly. `Reclaim`: SQLite `PRAGMA incremental_vacuum(256)` (v1 `vacuumPages`) outside any transaction; Postgres a no-op (autovacuum). `sqlite.Open` converts the file to `auto_vacuum = INCREMENTAL` once (v1 `bus.go:181-200`, the step Milestone 2 parked), after `sqlstore.Open` so the `VACUUM` that persists the mode runs on a file with tables.
5. **Budget settings and jobs.** The v1 names stay: `sqlite_budget_mib` (2048, bounds 64..1048576) and `cleanup_free_percent` (25, bounds 5..90), as `core.Config.SQLiteBudgetMiB` and `CleanupFreePercent` and as `internal/server/config` settings. The name says what it governs (pending item 2: the budget applies where `Usage.Evictable`, which is SQLite). Two jobs after "memory expiry" and before "embeddings" (v1 order): "budget eviction" (v1 `evictToBudget`'s sweep with its hysteresis: only when usage exceeds the budget does it sweep, and then down to the target `budget - budget*percent/100` (`cleanup_free_percent` is how far below the budget a sweep goes once the budget is exceeded, never the line at which sweeping starts; at or below the budget nothing is deleted), deleting the oldest ordinary messages a chunk at a time through `deleteOrdinaryChunk`, extracted from `messageRetention`, `Reclaim`, re-read usage; then `Reclaim` once more unconditionally, which is v1's "vacuum" step folded in) and "capacity notices" (spec 5.7's name, the one `TestMaintenanceRunJobRejectsUnknown` on `main` already rejects as unknown; set `notices.capacity` when usage still exceeds the budget, clear it otherwise). v1's inline `checkCapacity` before writes is pending item 3.
6. **Admin usage on the wire** (spec 3.2 admin row; Milestone 4 choice 1 deferred it here). `GET /v1/admin/usage` (`adminUsage`, tag `admin`, admin flag required) → `Usage{bytes, budget_bytes, evictable, notice?}`; `bus.Admin.Usage(ctx) (bus.Usage, error)`; the rule in `channels.Service.Usage` beside `Status`. `Status` is unchanged (Decision 48 names usage as its own operation).
7. **Docker.** Multi-stage `Dockerfile`: `golang:1.27-alpine` builder pinned by digest, `CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X github.com/ericfitz/agentbus2/internal/version.Version=${VERSION}"`, runtime `gcr.io/distroless/static-debian12:nonroot` pinned by digest, `ENTRYPOINT ["/agentbus2", "server"]` and an empty `CMD`, so `docker run <image> -registration enrollment` passes the Decision 58 override straight through and `docker exec <ctr> /agentbus2 server admin ...` bootstraps; `/data` (SQLite file, default `AGENTBUS2_SERVER_SQLITE` unset) and `/keys` (signing key) owned by `nonroot` so named volumes inherit a writable owner. Configuration by `AGENTBUS2_SERVER_*` variables or a mounted `-config` file (Decision 85). The compose example runs `postgres:17` and two replicas sharing a `keys` volume, the same `issuer` and the same `signing_key_file`, listening on `0.0.0.0:8420` inside the network; **8420 is the example's port only**: the spec decides no port and the server has no default (Milestone 4 choice 14). Image publishing is Milestone 9's.
8. **Replica semantics the ops docs state** (no code): a watch is a plain long-poll any replica serves, so no session affinity is needed; replicas must share `issuer` and `signing_key_file` (a bearer minted by one carries that `iss` and `kid`); the `jti` replay set (pending item 4) and the rate-limit buckets (Milestone 2 Gate 0 item 5) are per process, so N replicas each accept one reuse of a still-valid assertion and each grant the full per-identity rate.
9. **Exit test design.** `TestReplicasWake` starts two real `cmd.Run` commands over one database and proves the wake and the replaced answer across them; `TestReplicasMaintenanceExclusive` starts two `cmd.Serve` instances with a `Config.OnTick` observer (a report per tick is unreachable through `Run`) and proves one holder and failover. Both run under `dbtest.ForEachEngine`, so the subtest path always carries the engine segment the exit script and the self-test blocks grep for. `TestReplicasMaintenanceExclusive` has the same two leaves on both engines (the SQLite lease row and the Postgres session lock are both real cross-process locks). `TestReplicasWake` has five leaves on Postgres and three on SQLite: the shared key and issuer, the subscription through the other replica and the cross-server delivery have two-process meaning on both engines; the wake and the replaced answer cross servers only on Postgres (the exit criterion names Postgres), and the SQLite limitation of Milestone 4 choice 14 (two `agentbus2 server` processes over one SQLite file do not share hints; local multi-process mode is the Milestone 6 client's polling) stays pinned by Milestone 4's `TestWatchWakesAcrossProcesses` and `TestWatchReplacedAcrossProcesses`, not by a leaf that waits for nothing to happen. No engine's half is a skip.
10. **Docs layout.** `docs/ops/{README,deploy,configuration,admin-bootstrap,backup,upgrade}.md`; the configuration reference is checked mechanically against `config.Settings()` and `config.Default()` by a unit test (Definition of Done E).

## Claude proposal, pending Eric

Four points the frozen design leaves open; each proceeds on recommendation (A) with a `// pending Eric: Milestone 7 item N` marker on the test that encodes it. Task 7 records the answers in the ADR addenda.

1. **`NOTIFY` on watch registration.** Decision 52 puts `NOTIFY` inside the append transaction; Decision 68 says the newer watch marks the older one replaced through the shared database. Across two Postgres replicas, a watch on A replaced by a watch through B learns of it only at the next message hint or at its own timeout (up to 50 s; v1 issue #39's shape). A) `RegisterWatch` also notifies the schema channel with the control payload `0:0`, so the older watch answers `409 replaced` within the reconnect bound (recommended; one `pg_notify` per watch registration, hints only). B) No control notification; the ops doc states the bound. Encoded in Task 4's `TestPgnotifyHintOnWatchRegistration` and Task 7's `watch-replaced-across-servers` leaf.
2. **Budget eviction and capacity notices on SQLite only.** v1's budget protects a local file; on Postgres `pg_total_relation_size` includes dead tuples until vacuum, so an eviction loop that re-measures never sees the size fall and would delete ordinary messages tick after tick until none remain. A) The jobs act only where `Usage.Evictable` (SQLite); on Postgres `Usage` is reported for the admin operation and the notice is never set; the setting keeps its v1 name `sqlite_budget_mib` (recommended). B) Evict on Postgres too, bounded per tick by the estimated bytes of the deleted rows, accepting the runaway under bloat. C) Postgres eviction only when the `pgstattuple` extension is installed (an advertised capability). Encoded in Task 5's `TestMaintenanceBudgetEviction` (the Postgres half asserts nothing is deleted and no notice is set).
3. **v1's `checkCapacity` before every write is not ported.** v1 evicted inline and refused the write with `capacity_exhausted` when still over budget; Milestone 3's code set has no such code and adding one touches the OpenAPI enum and the remote mapping. A) Tick-only eviction; writes are never refused; the notice reaches agents through `receive` (Milestone 3 Task 10) and operators through `admin usage`; a burst can exceed the budget by at most `send_kib_per_second * maintenance_interval_seconds` per identity (recommended). B) Port it with a new code `capacity_exhausted` (HTTP 507) in the schema. Encoded in Task 5's `TestMaintenanceCapacityNotice` (a `Send` while the notice is set succeeds).
4. **The assertion `jti` replay set stays per process.** Milestone 5 choice 4 deferred a shared table to this milestone "if replicas need it". A) Keep it per process and document the bound: each replica accepts one reuse of an assertion still within `assertion.MaxLifetime` plus leeway (5 min + 60 s) (recommended; no version 3 migration, no write per token request). B) A `assertion_jti` table consulted and written in the token transaction. Encoded in Task 7's ADR 0002 addendum and `docs/ops/deploy.md`; no test marker (no code changes under A).
