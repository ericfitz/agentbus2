# Signing keys

The server signs the bearers it issues (`/v1/auth/token`, the human sign-in) with a key from its signing key set: rows in the `signing_keys` table, one active and any number retiring. The active key signs; every key in the set is published at `/v1/auth/jwks` and verifies until it is removed. The `provider` column says where the private key lives.

## Providers

`signing_key_uri` (`configuration.md`) picks the provider for this server:

| Value | Provider | Private key |
|---|---|---|
| unset | Store row | In the `signing_keys` row, PKCS#8 PEM in clear, EdDSA. The server generates it. |
| `awskms://...`, `gcpkms://...`, `azurekms://...`, `hashivault://...` | External | In the key service. The row holds the public key and the key reference (`provider_ref`); the server asks the service to sign. ECDSA P-256 (ES256) only: any other key type is refused when the URI is resolved. |

A scheme whose backend is not compiled into the binary stops the start with `the <scheme> backend is not in this build (build with -tags <scheme>)` (exit 2). Each backend is behind a build tag of the same name, so the default binary links no cloud SDK. The `awskms`, `hashivault`, `gcpkms` and `azurekms` backends are described below.

## awskms

Build: `go build -tags awskms .` (the default binary and the release archives link no AWS SDK; the Docker image's `Dockerfile` builds with no tag at present).

- Key URI: `awskms://[endpoint]/{key-id|key-ARN|alias/NAME|alias-ARN}`, for example `awskms:///alias/agentbus2` or `awskms:///arn:aws:kms:us-east-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab`. The optional `endpoint` is `host[:port]` and is always reached over https (for a VPC endpoint or a compatible service); leave it empty for the regional AWS endpoint. A URI that does not match is refused at start (exit 2).
- The key: an AWS KMS asymmetric key with key spec `ECC_NIST_P256`, usage `SIGN_VERIFY`, state `Enabled`. Another key spec, a disabled key or another usage is refused when the URI is resolved.
- Credentials and region come from the AWS SDK default chain (environment, shared config, container or instance role); set `AWS_REGION` or a profile region. The server stores none.
- What the server calls: `kms:DescribeKey` and `kms:GetPublicKey` when it resolves the URI (a rotation, the first start with no row, each scheduled-rotation tick) and again, at most every five minutes, before it signs (sigstore's signer re-reads them), and `kms:Sign` per bearer. Grant exactly those three actions on the key. Nothing else: the server never creates a key or an alias and never schedules a key's deletion.
- `AWS_TLS_INSECURE_SKIP_VERIFY` is not supported: sigstore honors it when signing but the key lookup does not, so the two would disagree; use a trusted certificate on the endpoint.
- Pinning: `rotate` resolves the key id or alias to the key's ARN and stores `awskms://[endpoint]/<key ARN>` as the row's key reference, so a bearer is always signed by the key whose public half the row holds, even after the alias moves.
- Rotating: create a new key and either repoint the alias (`aws kms update-alias --alias-name alias/agentbus2 --target-key-id <new key>`) or change `signing_key_uri` to the new key and restart, then run `agentbus2 server admin signing-key rotate`. The previous key stays in the set, and signable by its pinned ARN, until its `remove-after`; the operator retires it in KMS after that. Removal never deletes the external key.
- Failures: an unreachable endpoint, a timeout, throttling or an AWS 5xx is the service's own failure: `rotate` answers `unavailable` (retryable) and the token endpoint answers 503 `temporarily_unavailable`. Bad credentials, a missing, disabled or wrong-type key and access-denied answers are not retryable; `rotate` reports the AWS message with the key name, never the URI. A first start with no row exits 1 for either kind (`signing key: ...`); a malformed URI exits 2. The SDK retries a request up to three times before giving up, and a bearer's sign call is bounded to 10 seconds.
- Trust boundary: whoever may call `kms:Sign` on the key as the server's role can mint a bearer for any identity. Keep that permission on the server's role alone and audit it with CloudTrail.

## hashivault

Build: `go build -tags hashivault .` (the default binary and the release archives link no Vault client; the Docker image's `Dockerfile` builds with no tag at present). The backend works with HashiCorp Vault and with OpenBao (same API); the URI scheme is `hashivault` for both, and `openbao://` is refused.

- Key URI: `hashivault://NAME`, the name of a key in Vault's transit secrets engine, for example `hashivault://agentbus2`. `NAME` is letters, digits, `_`, `-` and `.`, starting and ending with a letter, digit or `_`. Anything else (a path, a query, user info, a trailing slash) is refused at start (exit 2), and the refusal does not print the URI.
- The key: a transit key of type `ecdsa-p256` that supports signing. Another type (`ed25519`, `ecdsa-p384`, RSA), a missing key or a key whose latest version has no readable public key is refused when the URI is resolved.
- Environment, read each time the backend connects (a running process cannot see a changed value, so replace a token by restarting):
  - `VAULT_ADDR`, else `BAO_ADDR`: the Vault address, `http` or `https` with a host and no user info (required);
  - `VAULT_TOKEN`, else `BAO_TOKEN`: the Vault token (required). The Vault CLI's token helper and `~/.vault-token` are not used, and the server does not log in or renew the token: use a token that outlives the process, such as a periodic token renewed outside the server;
  - `TRANSIT_SECRET_ENGINE_PATH`: the transit mount, default `transit`; slash-separated names (`team/transit`) with no leading or trailing slash. The mount is not part of the pinned key reference, so keep it the same on every replica;
  - the Vault client's own variables also apply: `VAULT_NAMESPACE`, `VAULT_HEADERS`, `VAULT_CACERT`, `VAULT_CACERT_BYTES`, `VAULT_CAPATH`, `VAULT_CLIENT_CERT`, `VAULT_CLIENT_KEY`, `VAULT_SKIP_VERIFY`, `VAULT_TLS_SERVER_NAME`, `VAULT_PROXY_ADDR` (which supersedes `VAULT_HTTP_PROXY`) and the standard `HTTP_PROXY` family. `VAULT_CLIENT_TIMEOUT` is parsed but does not set a timeout, and the server sets no retries (one attempt per request). A malformed value of any of them fails the connection (not retryable);
  - an `http://` address sends the token in clear: use `https://` except on a loopback or otherwise trusted link.
- Time bounds: resolving the key (a `rotate`, the first start, a scheduled-rotation tick) is limited to 30 seconds, for every backend; a bearer's sign call is limited by the issuer's 10-second deadline. A stuck connection can outlive its deadline inside sigstore's signer, which cannot be canceled; the 16-request limit below caps those.
- What the server calls: a read of `transit/keys/NAME` when it resolves the URI (a rotation, the first start with no row, each scheduled-rotation tick) and, at most every five minutes, before it signs (sigstore's signer reads the key to learn its type); and a write to `transit/sign/NAME/sha2-256` per bearer, asking for a pre-hashed ECDSA signature by the pinned version. The policy is exactly: `path "transit/keys/NAME" { capabilities = ["read"] }` and `path "transit/sign/NAME/sha2-256" { capabilities = ["update"] }` (with your mount in place of `transit`). The server never creates, rotates or deletes a key.
- Pinning: `rotate` reads the key's `latest_version` and stores `hashivault://NAME/VERSION` as the row's key reference, so a bearer is always signed by the version whose public half the row holds, even after you add a version in Vault. The version, not the key, is what a rotation changes.
- Rotating: add a version in Vault (`vault write -f transit/keys/NAME/rotate`) or point `signing_key_uri` at another key and restart, then run `agentbus2 server admin signing-key rotate`. The previous version stays in the set, and signable by its pinned version, until its `remove-after`; after that you retire it in Vault yourself (for example by raising the key's `min_encryption_version`). Removal never deletes the Vault key or a version.
- Wrong key: after Vault signs, the server verifies the signature under the key the row holds; a signature that does not verify (a replica with another `TRANSIT_SECRET_ENGINE_PATH` or `VAULT_NAMESPACE`, or a key deleted and recreated under the same name) is a non-retryable error. Vault's error text in messages is limited to 256 bytes and the token is replaced by `[redacted]`; a dial error shows the Vault `host:port`.
- Failures: Vault unreachable, a timeout, HTTP 429, any 5xx and a sealed or standby node (HTTP 503) are the service's own failure: `rotate` answers `unavailable` (retryable) and the token endpoint answers 503 `temporarily_unavailable`. A bad or expired token (403), a missing key, a key of another type and a key whose latest version cannot be read are not retryable; `rotate` reports Vault's message with the key name, never the URI, the token or the request URL. A first start with no row exits 1 for either kind (`signing key: ...`); a malformed URI exits 2. At most 16 sign requests may wait on Vault at once (sigstore's signer cannot be canceled, so a Vault that never answers is not allowed to strand more); beyond that a sign fails at once as `unavailable`.
- Trust boundary: whoever holds a token that may update `transit/sign/NAME/sha2-256` can mint a bearer for any identity. Keep that token on the server alone and audit it with Vault's audit device.

## gcpkms

Build: `go build -tags gcpkms .` (the default binary and the release archives link no Google SDK; the Docker image's `Dockerfile` builds with no tag at present).

- Key URI: `gcpkms://projects/PROJECT/locations/LOCATION/keyRings/RING/cryptoKeys/KEY`, optionally followed by `/cryptoKeyVersions/VERSION` (a number of 1 or more), for example `gcpkms://projects/my-project/locations/global/keyRings/agentbus2/cryptoKeys/token-signing`. Each name is letters, digits, `_` and `-` (a project may also hold `.` and `:`). User info, a query, a fragment, a trailing slash, any other path segment and sigstore's `/versions/V` spelling are refused at start (exit 2), and the refusal does not print the URI.
- The key: a Cloud KMS key with purpose `ASYMMETRIC_SIGN` and algorithm `EC_SIGN_P256_SHA256`. With no version in the URI, `rotate` pins the `ENABLED` version with the highest number; with one, that version, which must be `ENABLED`. Another algorithm (P-384, Ed25519, RSA), another purpose, a missing key or no `ENABLED` version is refused when the URI is resolved (not retryable).
- Credentials: Application Default Credentials, found the way the Google client libraries find them, in this order: the file named by `GOOGLE_APPLICATION_CREDENTIALS` (a service account key, an authorized-user file, a workload identity federation configuration or an impersonated service account), then `~/.config/gcloud/application_default_credentials.json` (`%APPDATA%\gcloud\...` on Windows), then the metadata server of a Compute Engine, GKE or Cloud Run host (`GCE_METADATA_HOST` overrides its address). The server stores none, and asks for the `cloud-platform` scope. Other variables the libraries read and that therefore apply: `GOOGLE_CLOUD_QUOTA_PROJECT`, `GOOGLE_CLOUD_UNIVERSE_DOMAIN`, `GOOGLE_API_USE_CLIENT_CERTIFICATE`, `GOOGLE_API_USE_MTLS_ENDPOINT`, `GOOGLE_API_USE_MTLS` (deprecated spelling of the mTLS switch), `EXPERIMENTAL_GOOGLE_API_USE_S2A`, `GOOGLE_AUTH_TRUST_BOUNDARY_ENABLED`, `GOOGLE_CLOUD_PROJECT` (the project ID the credentials report, when the credentials file names none), `GOOGLE_CLOUD_DISABLE_DIRECT_PATH`, `GOOGLE_CLOUD_ENABLE_DIRECT_PATH_XDS` and `GOOGLE_CLOUD_ENABLE_DIRECT_PATH_XDS_OVER_INTERCONNECT` (Direct Path routing), and for a federation file `AWS_*` and `GOOGLE_EXTERNAL_ACCOUNT_ALLOW_EXECUTABLES` (set to `1` to let the file run an executable; the server never sets it). The gRPC connection to Cloud KMS follows the standard proxy variables (`HTTPS_PROXY`, `NO_PROXY`). The server has no setting for an endpoint or a credentials path of its own. Leave `GOOGLE_SDK_GO_LOGGING_LEVEL` unset: the Google libraries read it, and at `debug` they log requests and responses.
- What the server calls (IAM permissions): `cloudkms.cryptoKeys.get` and `cloudkms.cryptoKeyVersions.get` and `cloudkms.cryptoKeyVersions.viewPublicKey` when it resolves the URI (a rotation, the first start with no row, each scheduled-rotation tick), plus `cloudkms.cryptoKeyVersions.list` when the URI names no version; the same `get` and `viewPublicKey` reads once when a signer first signs (sigstore caches a pinned version for that signer's life); and `cloudkms.cryptoKeyVersions.useToSign` per bearer (`AsymmetricSign` with a SHA-256 digest). Grant exactly those on the key. The server never creates a key, a version or a key ring and never schedules a version's destruction. The permission names are from Google's IAM reference, not from the client modules, so check them against the role you grant.
- The signer's gRPC connection to Cloud KMS is held for the life of the process and never closed (the sigstore signer has no `Close`); one connection per signer.
- Pinning: `rotate` stores `gcpkms://.../cryptoKeys/KEY/cryptoKeyVersions/VERSION` as the row's key reference, so a bearer is always signed by the version whose public half the row holds, even after you add or disable versions in Cloud KMS.
- Rotating: create a new version (`gcloud kms keys versions create --key KEY --keyring RING --location LOCATION`) or point `signing_key_uri` at another key and restart, then run `agentbus2 server admin signing-key rotate`. The previous version stays in the set, and signable by its pinned version, until its `remove-after`; after that you disable or destroy it in Cloud KMS yourself. Removal never touches the Cloud KMS key. A version you disable or destroy while it is still in the set can no longer sign, and `rotate` then fails for a URI that names it.
- Wrong key: after Cloud KMS signs, the server verifies the signature under the key the row holds; one that does not verify is a non-retryable error. A pinned version name is unique across Cloud KMS, so this is a guard, not an expected case.
- Time bounds: resolving the key (a `rotate`, the first start, a scheduled-rotation tick) is limited to 30 seconds, for every backend, and makes one attempt per request (no client retry). A bearer's sign call is limited by the issuer's 10-second deadline; inside it the Cloud KMS client retries an `Unavailable` or `DeadlineExceeded` answer with backoff. Reading the key the first time a signer is used runs on a context sigstore does not take from the caller, so it ends at the client's own 60-second per-call limit; a sign abandoned at its deadline leaves that read running to its end. At most 16 sign requests may be outstanding at once; beyond that a sign fails at once as `unavailable`.
- Failures: gRPC `Unavailable`, `DeadlineExceeded`, `ResourceExhausted`, `Internal` and `Unknown`, an unreachable endpoint, and a credential fetch that hit the network or a timeout (the metadata server unreachable, answering 429 or 5xx, or too slow) are the service's own failure: `rotate` answers `unavailable` (retryable) and the token endpoint answers 503 `temporarily_unavailable`. `PermissionDenied`, `Unauthenticated`, `NotFound`, `InvalidArgument`, `FailedPrecondition`, no credentials found, a malformed credentials file, a key of another algorithm or purpose and no `ENABLED` version are not retryable; `rotate` reports Cloud KMS's message (cut at 256 bytes, and with the access token replaced by `[redacted]`) with the key name, never the URI. A first start with no row exits 1 for either kind (`signing key: ...`); a malformed URI exits 2.
- Trust boundary: whoever may call `AsymmetricSign` on the key as the server's identity can mint a bearer for any identity. Keep `useToSign` on the server's service account alone and audit it with Cloud Audit Logs (data access logs for Cloud KMS).

## azurekms

Build: `go build -tags azurekms .` (the default binary and the release archives link no Azure SDK; the Docker image's `Dockerfile` builds with no tag at present).

- Key URI: `azurekms://VAULT-HOST/KEY`, optionally followed by `/VERSION`, for example `azurekms://my-vault.vault.azure.net/token-signing`. `VAULT-HOST` is the vault's DNS name: 3 to 24 letters, digits and hyphens (starting and ending with a letter or digit) under `vault.azure.net`, `vault.azure.cn`, `vault.usgovcloudapi.net`, `managedhsm.azure.net`, `managedhsm.azure.cn` or `managedhsm.usgovcloudapi.net`. `KEY` is letters, digits and `-` (up to 127). `VERSION` is the 32 lowercase hex digits Key Vault assigns. User info, a port, an IP address or any other host, a query, a fragment, a trailing slash, any other path segment and a version in another form (`latest`, upper case) are refused at start (exit 2), and the refusal does not print the URI.
- The key: an `EC` (or `EC-HSM`) key on curve `P-256` whose key operations include `sign`, enabled, and inside its not-before and expiry times. With no version in the URI, `rotate` pins the key's current version (the one Key Vault answers for the key name); with one, that version. A key of another type or curve (P-384, P-521, P-256K, RSA, oct), without the `sign` operation, disabled, expired, not valid yet, or missing is refused when the URI is resolved (not retryable). The answer's key identifier must name the same vault, key and (when the URI has one) version, or the answer is refused.
- Credentials: the Azure SDK's default credential chain (`azidentity.DefaultAzureCredential`, azidentity v1.14.1), tried in this order until one gives a token: environment, workload identity, managed identity, the Azure CLI (`az`), the Azure Developer CLI (`azd`) and Azure PowerShell (`pwsh`). The server stores none. The variables the chain reads, checked against the module source:
  - `AZURE_TOKEN_CREDENTIALS` is required: `prod` (environment, workload identity, managed identity), `dev` (the three CLI credentials) or one credential's name (`EnvironmentCredential`, `WorkloadIdentityCredential`, `ManagedIdentityCredential`, `AzureCLICredential`, `AzureDeveloperCLICredential`, `AzurePowerShellCredential`). With it unset or empty the start refuses `azurekms://` (exit 2), because without it the chain, after the first three fail, would run `az`, `azd` or `pwsh` from the server's `PATH` and pick up any `az login` session of the service account; any other value makes building the credential fail with an error naming the variable (not retryable).
  - Environment credential: `AZURE_TENANT_ID` and `AZURE_CLIENT_ID` with either `AZURE_CLIENT_SECRET`, or `AZURE_CLIENT_CERTIFICATE_PATH` (with `AZURE_CLIENT_CERTIFICATE_PASSWORD` and `AZURE_CLIENT_SEND_CERTIFICATE_CHAIN`), or `AZURE_USERNAME` with `AZURE_PASSWORD`.
  - Workload identity (for example on Kubernetes): `AZURE_TENANT_ID`, `AZURE_CLIENT_ID` and `AZURE_FEDERATED_TOKEN_FILE`; through a token proxy also `AZURE_KUBERNETES_TOKEN_PROXY`, `AZURE_KUBERNETES_CA_FILE`, `AZURE_KUBERNETES_CA_DATA` and `AZURE_KUBERNETES_SNI_NAME`.
  - Managed identity: `AZURE_CLIENT_ID` picks a user-assigned identity; the host sets `IDENTITY_ENDPOINT`, `IDENTITY_HEADER`, `IDENTITY_SERVER_THUMBPRINT`, `IMDS_ENDPOINT`, `MSI_ENDPOINT`, `MSI_SECRET` and `DEFAULT_IDENTITY_CLIENT_ID` (App Service, Functions, Service Fabric, Arc, Cloud Shell and Azure ML); a virtual machine reaches the instance metadata service at 169.254.169.254 with none of them.
  - All credentials: `AZURE_ADDITIONALLY_ALLOWED_TENANTS` (a `;`-separated list), `AZURE_REGIONAL_AUTHORITY_NAME` and `MSAL_FORCE_REGION` (regional sign-in endpoints).
  - The CLI credentials run `az`, `azd` or `pwsh` from the server's `PATH` with that user's sign-in (`az` reads `AZURE_CONFIG_DIR`; the server does not).
  - `AZURE_ENVIRONMENT` is read by the server: `AZUREPUBLICCLOUD` or `AZURECLOUD` (the default), `AZUREUSGOVERNMENT` or `AZUREUSGOVERNMENTCLOUD`, or `AZURECHINACLOUD` picks the cloud whose sign-in authority the credential uses; any other value is the public cloud, as in sigstore. A sovereign-cloud vault host (`.azure.cn`, `.usgovcloudapi.net`) needs `AZURE_ENVIRONMENT` set to match; the server does not cross-check them. On AKS workload identity the webhook-injected `AZURE_AUTHORITY_HOST` is ignored for the reason below, so without a matching `AZURE_ENVIRONMENT` the sign-in goes to the public authority and fails, without a retry. Because that choice always names an authority, `AZURE_AUTHORITY_HOST` has no effect.
  - The Azure SDK follows the standard proxy variables (`HTTPS_PROXY`, `NO_PROXY`). `AZURE_SDK_GO_LOGGING=all` makes it log requests to standard error; leave it unset. The server has no setting for a vault endpoint or a credential of its own.
- What the server calls (permissions): one `Get Key` (`GET /keys/KEY[/VERSION]`) when it resolves the URI (a rotation, the first start with no row, each scheduled-rotation tick); the same `Get Key` when a signer first signs and again after sigstore's 300-second cache of the public key expires; and one `Sign` (`POST /keys/KEY/VERSION/sign`, algorithm `ES256`, a SHA-256 digest) per bearer. In Azure RBAC for a vault those are the data actions `Microsoft.KeyVault/vaults/keys/read` and `Microsoft.KeyVault/vaults/keys/sign/action`; with an access policy, the key permissions Get and Sign; a managed HSM uses its own local RBAC roles for the same two operations. Grant exactly those on the one key (the built-in Key Vault Crypto User role grants more). The server never creates, updates or deletes a key or a version. The permission names are from Microsoft's reference, not from the SDK modules, so check them against the role you grant.
- TLS: the Azure SDK checks the vault's certificate against the system roots and requires the authentication challenge to name the vault's own domain (the SDK's check, left on).
- Pinning: `rotate` stores `azurekms://VAULT-HOST/KEY/VERSION` as the row's key reference, so a bearer is always signed by the version whose public half the row holds, even after you create or disable versions in Key Vault.
- Rotating: create a new key version (`az keyvault key rotate --vault-name VAULT --name KEY`, or import one), or point `signing_key_uri` at another key and restart, then run `agentbus2 server admin signing-key rotate`. The previous version stays in the set, and signable by its pinned version, until its `remove-after`; after that you disable or delete it in Key Vault yourself. Removal never touches the Key Vault key. A version you disable, or whose key you delete, while it is still in the set can no longer sign.
- Wrong key: after Key Vault signs, the server verifies the signature under the key the row holds; one that does not verify is a non-retryable error that names the likely causes (a replaced key version, a key that is not ES256, a reply that is not from Key Vault).
- Time bounds: resolving the key (a `rotate`, the first start, a scheduled-rotation tick) is limited to 30 seconds, for every backend, and makes one attempt (no retry in the Key Vault client; the credential's own Azure SDK pipeline keeps its default retries, inside the 30 seconds). A bearer's sign call is limited by the issuer's 10-second deadline. Sigstore's signer uses the Azure SDK's default retry (three retries from 0.8 seconds, on 408, 429, 500, 502, 503 and 504) inside it, and passes the call's context to every request. The sign runs in a goroutine so that a panic in sigstore's code (it dereferences the key type of a malformed reply unchecked) is an error and not the end of the server, and so that the caller returns at its deadline whatever the credential step is doing. At most 16 sign requests may be outstanding at once; beyond that a sign fails at once as `unavailable`.
- Failures: HTTP 408, 429 and 5xx from Key Vault or from the sign-in service, an unreachable or slow endpoint, and a context deadline are the service's own failure: `rotate` answers `unavailable` (retryable) and the token endpoint answers 503 `temporarily_unavailable`. 401, 403, 404 and other 4xx, no credential found, a malformed credential setting, and a key of another type, curve or state are not retryable; `rotate` reports the HTTP status and Key Vault's error code (cut at 256 bytes, with the access token and the credential secrets in the environment replaced by `[redacted]`) with the key name, never the URI or the response body. One limit: the default chain joins its members' errors into text, so a network failure inside the chain (for example the sign-in endpoint unreachable) reaches the server as an authentication failure with no response and is reported as not retryable; the next `rotate` or scheduled tick tries again. A first start with no row exits 1 for either kind (`signing key: ...`); a malformed URI exits 2.
- Two credentials: `rotate` builds one default chain, and sigstore's signer builds its own (the same chain, with the cloud chosen from `AZURE_ENVIRONMENT` the same way), so both read the same environment. The signer's chain is exercised only by the opt-in live test (`AGENTBUS2_LIVE_AZUREKMS_URI`); the unit tests replace sigstore's signer.
- Trust boundary: whoever may call `sign` on the key as the server's identity can mint a bearer for any identity. Keep the sign permission on the server's identity alone and audit it with the vault's diagnostic logs.

## Trust boundary

- Store-row provider: whoever can read the database (or a backup of it) can mint a token for any identity. The database is protected like the administrator credential (`deploy.md`, `backup.md`).
- External provider: the database holds no private key. Reading it does not let anyone mint. The boundary moves to the key service: whoever may call its sign operation with the server's credentials can mint, so grant the server's identity sign and read-public-key on that one key and nothing else. The server never creates, deletes or schedules deletion of an external key.

## Rotation

`agentbus2 server admin signing-key rotate` (or `POST /v1/admin/signing-keys/rotate`) asks the configured provider for its next key and makes it the active key; the previous active key becomes retiring and stays published until its `remove_after` (the API field; `signing-key list` prints it as `remove-after`: the reload interval, the longest bearer lifetime and the verification leeway after it stopped signing). `-revoke-previous` deletes it at once instead. `signing-key list` shows every row with its `remove-after`.

- Store row: the next key is a freshly generated one. `signing_key_rotation_hours` rotates it on schedule.
- External: the next key is the one the key URI resolves to now. The operator changes what the URI names (repoints the alias, adds a version, or points the setting at a new key and restarts), then runs `rotate`. Rotating while the URI still resolves to the active key answers a `conflict` (`the key URI resolves to the active signing key ...`) and changes nothing. While `signing_key_rotation_hours` is above 0 the `signing key rotation` job resolves the URI on every maintenance tick and adopts a repointed key within one tick; it cannot rotate the external key itself, so a key that is older than the interval and still named raises the job error shown in `health.md`. 0 turns scheduled rotation off for every provider.
- Removing a retiring row never touches the key service. After `remove-after` (shown by `signing-key list`) the operator retires the old key there.

## When the key service is down

- A start with an active row makes no call to the key service and serves: verification and the JWKS work, minting answers 503 `temporarily_unavailable` until the service returns (the next mint after it returns works with no restart).
- A start with no row calls the service once to adopt a key; if it cannot, the server exits 1 (a configuration error, such as a bad URI or a missing backend, exits 2). A start that failed this way left nothing behind and the next start retries.
- `rotate` and the scheduled job answer `unavailable` (retryable) and change nothing.

On a first start the server prints `adopted signing key <kid> (<provider> <key name>)`, where the key name is the URI without user info, query or fragment; the URI itself is never printed.
